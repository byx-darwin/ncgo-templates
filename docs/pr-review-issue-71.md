# Phase 4 Gate-Check Review — Issue #71 Forgot-Password Self-Reset

- **Scope**: merge commit `170bf7e` ("Merge branch 'feat/71-forgot-password-self-reset'" into `main`), diffed against its first parent `03e6b20` (merged tip `8880feb`).
- **Context**: this feature already went through 11 independently-reviewed TDD tasks plus a final whole-branch review (one merge-blocking fix already applied: rejecting empty identifiers in `RequestPasswordReset`, commit `8880feb`). This review is an independent final gate-check, focused on what a fast implementation-time review might miss — security, resource leaks, cross-file consistency, edge cases — rather than re-litigating the primary review.
- **Method**: read the full merged diff (25 files, ~1076 insertions) directly via `git show`/`git diff` against the first parent — `user.proto` (both services), `user_service.go` (RequestPasswordReset/ConfirmPasswordReset/setPassword), `passwordreset/repository.go` (SQL + in-memory), `notify/sender.go` stub, DB migrations 000003/000004 + queries, `server.go` wiring, BFF `auth.go` handlers, router registration, rate-limit config/resolver, and the accompanying test files (service, router, repository, admin fakes). Did not attempt to run `go build`/`go test` — this is a template repo where the `.go.yaml` files are rendered by `ncgo`, not directly compilable in place; correctness was assessed by close reading.

## Findings

### 1. (Low-Moderate) No audit trail for failed `ConfirmPasswordReset` attempts
`ConfirmPasswordReset` (`user-kitex/kitex-template/internal_application_user_user_service_go.yaml`) returns a generic error on any invalid/expired/reused credential but never calls `s.audit.Write(...)` on that path. This is inconsistent with the sibling `setPassword` old-password-verification failure, which explicitly writes a `user.password_change.failure` audit entry "so brute-force attempts are visible in the audit trail." The SMS channel issues a 6-digit numeric code (1,000,000 possibilities) with a 5-minute TTL; the only defense against guessing is a per-IP rate limit (10 req/hour on `password_reset_confirm`). A distributed attacker spread across multiple source IPs would leave literally zero audit signal while attempting to brute-force a code. Recommend adding a `user.password_reset_confirm.failure`-style audit entry (without leaking which specific reason it failed, to preserve the anti-enumeration property) so this is at least visible to security monitoring.

### 2. (Low) TOCTOU on token redemption
`ConfirmPasswordReset` performs `GetValid` → `setPassword` → `MarkUsed` as three independent, unlocked calls (true for both `SQLRepository`, which issues a plain `SELECT ... WHERE used_at IS NULL AND expires_at > now()` with no `FOR UPDATE`/atomic consume, and `MemoryRepository`, which locks its mutex per-method-call, not across the three calls). Two concurrent requests carrying the same still-valid credential could both pass `GetValid` before either reaches `MarkUsed`, letting the token be "used" twice (e.g., setting two different passwords in a race) before invalidation lands. Real-world severity is low — whoever holds the credential already has full reset capability — but it's a straightforward fix (`UPDATE ... WHERE credential_hash = $1 AND used_at IS NULL AND expires_at > now() RETURNING *` as a single atomic consume-and-fetch) if tightened.

### 3. (Informational / likely accepted risk) SMS code brute-force surface
Related to #1: a 6-digit code space with only IP-based, not per-token/per-user, rate limiting on the confirm endpoint means the code's real protection is TTL (5 minutes) plus the practical friction of distributing an attack across IPs. This is presumably an accepted tradeoff given `notify` is explicitly a stub pending a real SMS provider, but flagging so it isn't lost before the real provider integration ships (e.g., consider a per-token failed-attempt counter that invalidates the token after N wrong guesses).

## Not Findings (verified clean)

- **Anti-enumeration correctness**: `RequestPasswordReset` returns `nil` uniformly for empty identifier, not-found, lookup error, invalidate error, generate error, store error, and send error — only a structurally invalid `channel` value returns an error, which is a client-side contract violation, not an account-existence signal. Confirmed by tests (`TestRequestPasswordReset_UnknownIdentifier_StillSucceedsNoSend`, `TestRequestPasswordReset_EmptyIdentifier_NoOpNoSend`).
- **Empty-identifier fix** (the one merge-blocking issue from the prior whole-branch review) is present and covered by a regression test with a clear explanatory comment about the `email <> '' `/`phone <> ''` unique-index interaction.
- **Credential storage**: raw tokens/codes are never persisted — only `sha256` hex digests (`hashCredential`), matching the schema comment and the `passwordreset.Token` doc comment.
- **Token generation**: uses `crypto/rand` (not `math/rand`) for both the 32-byte URL-safe email token and the 6-digit SMS code — correct choice called out explicitly in a doc comment.
- **Session invalidation on reset**: `ConfirmPasswordReset` → `setPassword` → `s.blacklist.Revoke(ctx, uid)`, so existing JWTs are revoked when a password is reset via this path, same as self-service change-password.
- **Old-token invalidation**: `RequestPasswordReset` calls `InvalidateForUser` before minting a new token, and this is covered by `TestRequestPasswordReset_SecondRequest_InvalidatesFirstToken`.
- **DB constraints**: new `password_reset_tokens` table has a `UNIQUE` index on `credential_hash` (collision-safe given SHA-256) and an index on `user_id`; foreign key is `ON DELETE CASCADE`. The new partial unique indexes on `users.email`/`users.phone` (`WHERE email <> ''` / `WHERE phone <> ''`) correctly avoid breaking existing rows that share the default empty string, and also correctly exclude NULL rows (Postgres never indexes NULL in a unique index), consistent with the nullable `TEXT` columns in `000001`.
- **Resource management**: `notify.LogEmailSender`/`LogSMSSender` and `passwordreset.MemoryRepository` all guard shared state with `sync.Mutex` and return defensive copies from their `Sent()` accessors — no leaks, no data races found by inspection.
- **Rate-limit wiring**: `password_reset_request` (5/hour/IP) and `password_reset_confirm` (10/hour/IP) phases are threaded consistently through `conf.yaml` → `RateLimitConfig` struct → `resolver.go`'s phase switch → router registration; both endpoints are correctly placed outside the `authProtected` JWT-required group (a locked-out user has no token), and this placement is asserted by `TestPasswordResetRequest_AlwaysSucceeds_NoAuthRequired`.
- **Cross-file consistency**: `RequestPasswordResetReq`/`ConfirmPasswordResetReq`/`Resp` messages, RPC signatures, generated-handler stubs, BFF request DTOs, and README endpoint tables all agree with each other across both `user-kitex/idl/user.proto` and `user-bff-hertz/idl/user.proto`.
- **Known pre-existing gap, not newly introduced**: the router test file (`internal_router_userbffservice_test_go.yaml`) documents in a comment that `response.Err` currently maps any business error to HTTP 500 rather than its real status code, because `response.Err`/`response.OK` use the package-level `Error()`/`Success()` helpers instead of the per-request `Responder` with `RPCErrorRouter` wired in server middleware. This affects `Register`/`Login`/`ChangePassword` identically and predates this feature; the new endpoints inherit the existing behavior consistently rather than regressing it further. Left as a documented follow-up, correctly not treated as in-scope for this PR.

## Verdict

No Critical or blocking issues found. Two Low/Low-Moderate non-blocking findings (#1 audit-trail gap on failed confirms, #2 TOCTOU on token redemption) and one informational note (#3) are recommended as fast follow-ups but do not block this already-merged change.
