## Scope

Adds `admin-bff-hertz` Terminal (end-user) Account Management: `GET /api/v1/terminal-users`, `GET /:uid`, `POST /:uid/ban`, `POST /:uid/unban`, `DELETE /:uid/identities/:provider`, backed by two new `user-kitex` admin RPCs (`GetUser`, `AdminUnbindProvider`) added alongside the existing `ListUsers`/`BanUser`/`UnbanUser`/`ForceLogout`/`ListUserIdentities` admin surface. Also fixes a real, pre-existing, security-critical bug in `admin-bff-hertz`: the `Authz` (RBAC permission-check) middleware was registered at the `protected` route-group level via `.Use(...)`, ahead of every route's `RequirePermission(code)` call. Because Hertz's `RouterGroup.combineHandlers` always places group-level `Use()` handlers before a route's own handlers, `Authz` always ran before the required-permission code was set on the request context, always took its "nothing required" no-op branch, and silently skipped RBAC enforcement on **every** protected route in the package — all 19 pre-existing routes plus the 5 new terminal-user routes (24 total). The fix moves `Authz(rbacCli)` to run per-route, immediately after `RequirePermission(code)`, on all 24 gated routes.

This branch went through extensive internal review prior to this pass: per-task reviews during implementation, and a final whole-branch opus review that included adversarial live-server verification of the security fix and a small final fix-wave (`f3ea7e5`: gofmt import ordering, stale-doc corrections). This report is the formal Phase 4 delivery record, not a from-scratch adversarial pass; it independently re-verifies the security-critical surface and the new feature's correctness/coverage in the merged diff.

## Strengths

- **The Authz no-op bug fix is complete and verified by direct diff inspection**, not just by trusting the PR description. `grep -c "middleware.Authz(rbacCli)"` against the final router template returns 24, matching `grep -c "RequirePermission"` (26, minus the 2 occurrences that are code-comment prose, not real calls) — every permission-gated route, old and new, pairs `RequirePermission(code)` with `Authz(rbacCli)` immediately after it, on the same route registration line. No route was missed.
- **Regression tests directly exercise the bug class**, not just the new feature: `internal_router_adminbffservice_test_go.yaml` adds `TestAuthz_DeniedPermission_Returns403` / `TestAuthz_AllowedPermission_Returns200` for a pre-existing route and `TestTerminalUsersRoute_DeniedPermission_Returns403` / `TestTerminalUsersRoute_AllowedPermission_Returns200` for a new one — these would have failed (permission-denied requests would incorrectly return 200) under the pre-fix no-op ordering, which is exactly the kind of test that catches this class of bug on any future refactor of the route-registration code.
- **Trust boundary for the new `AdminUnbindProviderReq` RPC is explicit and consistent with the existing admin RPC surface.** Its proto comment states plainly that `user-kitex` does not re-verify caller identity for this call — authorization is entirely admin-bff-hertz's RBAC gate (`terminal_user:unbind-identity`) — matching the pre-existing `BanUser`/`UnbanUser`/`ForceLogout`/`ListUsers` pattern. This is correctly distinguished in the same proto file from `UnbindProviderReq` (self-service, uid must come from the caller's own verified JWT) and from the OAuth-bind-flow's previously-fixed `BindProviderReq` (Issue #65) — no confusion between the three uid-trust models.
- **`AdminUnbindProvider` reuses `UnbindProvider`'s business logic by delegation** rather than duplicating it (`h.self.UnbindProvider(ctx, req.Uid, req.Provider)`), so the "cannot unbind your only auth method" safety check applies identically regardless of caller (end-user self-service vs. admin-on-behalf-of). Avoids a class of bug where a new code path forgets an existing invariant.
- **`Ban`'s `ForceLogout`-is-best-effort design is deliberate and documented**, not an oversight: the ban itself (recorded in `user-kitex`'s database) is the source of truth and is never rolled back if `ForceLogout` fails; the failure is surfaced to the caller via a `force_logout_error` response field rather than as a 500, and the README documents the operational implication (tokens may remain valid until expiry if the backing `user-kitex`'s Redis blacklist is disabled). Test coverage (`TestTerminalUserHandler_Ban_ForceLogoutFailure_StillReturns200`) confirms this behavior is what actually ships.
- **Error-code handling in the new handler is consistent with every other existing admin-bff-hertz handler** (`menu`, `role`, `rate_limit`, `permission`, `auth`, `current_user` all map RPC/not-found errors to the same generic `response.CodeInternalError`), so `terminal_user.go`'s lack of a distinct not-found status is pre-existing convention, not new inconsistency introduced by this branch.

### Minor (Nice to Have)
1. `internal_handler_terminal_user_go.yaml`'s `List`/`Get`/`Ban`/`Unban`/`UnbindIdentity` all collapse every RPC error (not-found, invalid-argument, transport failure) to the same `response.CodeInternalError` (500). This matches the pre-existing convention across every other admin-bff-hertz handler in this repo (not a defect introduced here), but it means, e.g., `GET /terminal-users/:uid` for a nonexistent `uid` returns 500 rather than 404 — worth a follow-up across the whole handler package if finer-grained REST status mapping is ever desired, out of scope for this branch.
2. `admin-bff-hertz/README.md` now documents (accurately, per this branch's own fix-wave) that `rpc_timeout_seconds`/`connect_timeout_milliseconds`/`retry` in `grpc.terminal_user` are parsed into config but never actually applied to the Kitex client construction in `server.go` (which passes only `client.WithHostPorts`). This is an accurately-flagged pre-existing gap shared with `grpc.authority`, not introduced by this branch; noting only because it now affects a fourth RPC client (`terminal_user`) without being fixed.
3. `AdminUnbindProviderReq`/`GetUserReq` in `user-kitex`'s admin RPC surface (like the pre-existing `BanUser`/`UnbanUser`/`ForceLogout`/`ListUsers`) have no independent caller-identity check at the `user-kitex` layer — correctly documented as an accepted, consistent trust-boundary design (admin-bff-hertz's RBAC gate is the sole enforcement point), but it does mean a `user-kitex` instance reachable directly (bypassing admin-bff-hertz) has no defense in depth for these admin operations. Worth a network-segmentation/mTLS callout if not already covered by broader infra docs, not a code defect.
